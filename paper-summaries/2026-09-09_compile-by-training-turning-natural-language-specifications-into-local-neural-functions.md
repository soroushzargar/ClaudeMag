# Compile by Training: Turning Natural-Language Specifications into Local Neural Functions

**arXiv:** 2609.04199  
**Submitted:** September 2, 2026  
**Authors:** Yuntian Deng, Pengyu Nie, Stuart Shieber  
**Affiliation:** Harvard University; and collaborating institutions  
**Venue:** EMNLP 2026 System Demonstrations

---

## Headline Finding

Compile by Training (CbT) converts a natural-language specification into a reusable local neural function by using teacher LLMs to generate task-specific training examples at compile time and fine-tuning a compact adapter for a local interpreter — achieving 83.6% semantic accuracy on FuzzyBench-Hard (where a fast compiler produces zero exact matches) and producing artifacts that run locally, version like code, and compose like software.

---

## Key Findings (Pyramid Layer 2)

1. **Compilation beats runtime inference for reusable tasks.** When the same task will be invoked repeatedly, paying a higher compile-time cost (one minute) to produce a persistent local neural function is more efficient than repeated teacher LLM calls at runtime.
2. **Teacher-generated data enables deep specialization.** By having strong teacher LLMs enumerate diverse inputs and their correct outputs for a given specification, CbT creates task-specific training examples that drive the adapter far beyond the compact model's zero-shot capability.
3. **83.6% semantic accuracy on hard benchmarks.** On FuzzyBench-Hard — where existing fast compilation (Program-as-Weights) produces no exact matches — CbT achieves 83.6% semantic accuracy, demonstrating that training-time computation substitutes for runtime inference quality.
4. **Functions compose and version like software.** Compiled neural functions are stored weights that run without teacher access; multiple compiled functions can be chained, the outputs of one serving as inputs to the next, and versions can be stored and rolled back.

## Methodology (Pyramid Layer 3)

### Background: Program-as-Weights and Fast Compilation

The **Program-as-Weights (PAW)** framework treats a natural-language specification $s$ as a program and produces a neural function $f_\theta$ (a fine-tuned adapter) that implements it. A fast PAW compiler produces $f_\theta$ in seconds by directly fine-tuning on a small set of in-context examples generated by the teacher at query time.

However, fast PAW compilation achieves poor accuracy on hard specifications — tasks with complex logic, edge cases, or unusual output formats — because the small set of teacher-generated examples does not sufficiently cover the input space.

### Compile by Training (CbT)

CbT extends the PAW compilation paradigm with a more thorough training-time process:

**Step 1: Specification-driven example generation**  
Given a natural-language specification $s$, teacher LLMs (large frontier models) are queried to generate a diverse set of $(x_i, y_i^*)$ pairs where $x_i$ is a task input and $y_i^*$ is the correct output according to $s$. Multiple teachers are used in a committee to reduce individual teacher errors.

**Step 2: Example validation and filtering**  
Generated pairs are validated by cross-referencing: if $k$ out of $K$ teachers produce consistent outputs $y^*$ for an input $x$, the pair is accepted. Pairs with disagreement are discarded. This produces a curated dataset $\mathcal{D}_s = \{(x_i, y_i^*)\}_{i=1}^N$.

**Step 3: Adapter fine-tuning**  
A lightweight LoRA adapter $\delta\theta$ for a compact local interpreter model is trained on $\mathcal{D}_s$:
$$\mathcal{L}_{\text{CbT}} = -\sum_{(x,y^*) \in \mathcal{D}_s} \log p_{\theta + \delta\theta}(y^* | s, x)$$
The adapter is trained to implement $s$ as a deterministic function given inputs.

**Step 4: Deployment**  
The compiled function $(s, \delta\theta)$ is stored as an artifact. At inference time, only the compact local model with the adapter is required — no teacher access, no internet connectivity.

### Composition

CbT functions compose by chaining: if function $f_A$ implements specification $s_A$ and $f_B$ implements $s_B$, a composed function $f_{A \circ B}$ can be produced by:
1. Generating a composed specification $s_{A \circ B}$ describing the composed task.
2. Compiling $f_{A \circ B}$ using $f_A$ and $f_B$ to generate examples (running $f_A$ to produce intermediate inputs for $f_B$).

## Technical Formulation

### Semantic Accuracy Metric

Standard exact-match accuracy fails for tasks with multiple valid output forms. CbT is evaluated on **semantic accuracy**:
$$\text{SemAcc} = \frac{1}{N_{\text{test}}} \sum_{i=1}^{N_{\text{test}}} \mathbf{1}[\text{sem-equiv}(f_\theta(x_i), y_i^*)]$$
where sem-equiv is a semantic equivalence judgment (by a judge LLM), allowing different surface forms of the correct answer.

### Compile-Time Compute vs. Accuracy Tradeoff

Let $N_{\text{ex}}$ be the number of teacher-generated training examples. The authors show empirically that:
$$\text{SemAcc}(N_{\text{ex}}) \approx A - B \cdot \exp(-\alpha N_{\text{ex}})$$
fitting a saturation curve with parameters $A \approx 0.85$, $B \approx 0.84$, $\alpha \approx 0.003$ for FuzzyBench-Hard. The saturation point is around $N_{\text{ex}} = 1000$ examples.

### Teacher Disagreement Rate

The fraction of input examples discarded due to teacher disagreement:
$$d = 1 - \frac{|\mathcal{D}_s|}{N_{\text{generated}}}$$
A high disagreement rate signals an ambiguous specification; the authors propose using $d$ as a spec quality metric and prompting the user to clarify high-$d$ specifications.

## Experiments

### Benchmarks
- **FuzzyBench-Hard:** Complex natural-language specifications requiring fuzzy string matching, format normalization, and semantic transformation.
- **WebTask:** Website interaction helper tasks (form filling, content extraction).
- **Avatar-Control:** Language-controlled 3D avatar motion generation.

### Results

| Method | FuzzyBench-Hard (SemAcc) | Compile Time | Runtime |
|--------|--------------------------|-------------|---------|
| Teacher at runtime (GPT-4o) | 91.2% | 0 s | 2.1 s/query |
| PAW fast compiler | 0.0% (exact) / 51.3% (sem) | 8 s | 12 ms/query |
| **CbT (ours)** | **83.6%** | **~60 s** | **12 ms/query** |
| CbT + teacher validation | 87.1% | ~120 s | 12 ms/query |

CbT closes 80% of the gap between PAW and teacher-at-runtime quality while preserving the local, fast, offline runtime of PAW.

### Composition Experiment

Two-function compositions on WebTask achieve 76.4% task success rate with CbT, vs. 82.1% with a single teacher call for the composed task — confirming that composition is viable though incurs some compounding error.

---

## Ablations and Interpretation

- **Committee size (number of teachers):** Using 3 teachers reduces validation disagreement rate from 31% (1 teacher) to 12%, and improves SemAcc from 79.4% to 83.6%.
- **Training set size:** Saturation around 1,000 examples; 500 examples achieve 80.1% SemAcc, 2,000 add only 0.8 points over 1,000.
- **Adapter size (LoRA rank):** Rank 16 achieves full accuracy; rank 4 loses 2.1 points; rank 64 adds nothing.
- **Specification ambiguity:** High teacher disagreement rate ($d > 0.4$) predicts low SemAcc; prompting users to clarify those specifications recovers 4.3 points on average.
